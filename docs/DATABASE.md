# Database

**What this answers:** the rules that are expensive to rediscover. It does not
list the schema — `supabase/migrations/` in order is the schema, and
`src/lib/supabase/database.types.ts` (regenerated by `npm run db:types`) is its
TypeScript shadow.

---

## 1. Migrations

Four digits, sequential, in `supabase/migrations/`. There are 134 of them.

**A migration is never edited after it has been pushed.** Supabase records
applied migrations by version number, so editing one that is already applied
means the edit never arrives anywhere but your laptop. Fix it with a new
migration.

## 2. Nothing in CI applies them

`ci.yml` runs the suites against a fresh local stack. It does **not** touch the
hosted project, and there is no intention to automate that.

So every merge that carries a migration needs, by hand, the same day:

```bash
npx supabase migration list --linked     # local vs remote, side by side
npx supabase db push                     # --dry-run first if you want the list
```

This is not hypothetical. The hosted database has drifted **41 migrations**
behind once and **10** behind twice, and each time it was discovered by a screen
failing with `PGRST202` — "could not find the function" — which names no
migration and no deploy.

When probing a hosted RPC afterwards, note that PostgREST resolves overloads by
**argument name**: a call with an empty body answers `PGRST202` even when the
function is there. A 404 only means "missing" if the parameters were right.

## 3. Grants are not automatic

A table created by a migration grants nothing to anybody. `service_role`
bypasses RLS but **still needs ordinary table privileges**, and it does not
inherit them here.

Block 11b's `job_health` shipped without them in review and every read answered
`42501`, which would have left the alert route reporting a healthy installation
because it could not see the rows saying otherwise. `supabase/tests/25_job_health.test.sql`
now asserts the grants, and that is the pattern: **assert the grant, not just the
table.**

## 4. Procedure or function

- A **function** may not `commit`. A **procedure** may.
- A procedure that commits may carry **neither** `security definer` **nor** a
  `set` clause — Postgres refuses transaction control inside either, and the
  failure is `invalid transaction termination` at 04:11 where nobody is looking.
  `0094`, `0128` and `0131` each assert this about themselves.
- **No `exception` handler in anything that commits.** A `begin … exception …
  end` block opens a subtransaction, and `commit` inside one raises `cannot
  commit while a subtransaction is active`. Block 11a's retention sweep shipped
  with one per table, deleted nothing every night for a whole block, and the
  pgTAP suite was green throughout — because it asserts the *source*, and the
  procedure could not be executed inside a test transaction.

## 5. Which suite answers which question

| suite | runs as | answers |
| --- | --- | --- |
| `npm run db:test` (pgTAP) | superuser, null `auth.uid()`, transaction rolled back | does the object exist, does the logic hold, is the source what it should be |
| `npm run test:isolation` | real users over HTTP, and a direct connection for procedures | does RLS actually stop this, is the grant there, does the routine run |
| `npm run test` (Vitest) | no database | pure logic, schemas, route handlers |
| `npx playwright test` | a browser | the screens, and the seams between them |

**pgTAP cannot see a missing grant and cannot see a policy.** If a change is
about who may do something, the proof belongs in the isolation suite.

## 6. Extensions

`digest()` and friends live in the `extensions` schema, not `public`. A bare
`digest(...)` in a migration resolves to nothing; qualify it.

## 7. Two local-stack traps

- **`npm run db:test` needs a freshly reset database.** After an e2e or isolation
  run, `15_music_rpcs` fails with "more than one row returned by a subquery".
  That is state, not a regression: `npm run db:reset` first.
- **`supabase db reset` leaves Kong blind.** Every auth call then answers
  `createUser failed: {}` until `docker restart supabase_kong_<project>`.
