# Public legal pages — privacy, deletion and terms

**Status:** design agreed with the owner, 2026-08-13.
**Why now:** Meta requires a published privacy policy and a data-deletion
address before a WhatsApp Business integration is reviewed, and the LGPD
requires both regardless of Meta.

---

## 1. What this is for

Three pages, public, at fixed addresses:

```
pulchatx.com/privacy       Política de Privacidade
pulchatx.com/delete-data   Solicitação de Exclusão de Dados
pulchatx.com/terms         Termos de Serviço
```

Two are documents. The third is a document **and a form**: it is where a person
asks for their data to be deleted, and it must give them something to quote
afterwards.

All three must work with no session, in English, Portuguese and Spanish, and
read well on a telephone — the device most listeners will open them on, because
the link reaches them inside WhatsApp.

The owner supplied the Portuguese text. **It spells the product "PulChatX"
throughout and the product is "PulchatX"** — corrected everywhere, including in
the two other languages.

---

## 2. Decisions

The owner's, taken 2026-08-13.

**D1 — The legal text lives in content modules, not in the message
catalogues.** One module per document per locale, nine in all, under
`src/content/legal/`. The catalogues stay what they are: labels for controls.

Three reasons, in order of weight. A legal document is **content that changes as
a document** — a git diff of one amended paragraph is readable, while the same
change inside a 120 KB JSON catalogue is not. The catalogues are already
~120 KB each and next-intl loads one per request; three documents would roughly
double that on every page of the product, not only these. And
`tests/unit/i18n/usage.test.ts` requires a literal key at each call site, so a
forty-paragraph document becomes forty-plus keys per document per language —
which the test can check the existence of, and no reviewer can read.

**D2 — A deletion request gets its own table, its own protocol and its own
screen.** It is a legal obligation with a clock on it, not an enquiry.
`contact_requests` is where somebody asks about buying the product; mixing the
two would put a statutory deadline in the same inbox as a sales lead, and would
force the protocol to be a UUID, which nobody can read down a telephone.

**D3 — The form records a request. It deletes nothing.** The owner's own text
says an identity check comes first: *"poderemos realizar procedimentos para
confirmar a identidade ou legitimidade do solicitante"*. A public form that
erased data on submission would let anybody erase anybody's record by typing
their telephone number.

**D4 — The public layout gains a header.** Today it is a bare column. It gains
the PulchatX mark, links between the three documents, and a language selector —
and **no link into the authenticated product**, which a listener has no account
for. `/contato` shares that layout and inherits the header.

**D5 — No locale prefix in the URL.** The three addresses are fixed, because
they are what Meta records and what the policy itself cites. Language is
resolved as everywhere else in this product — cookie, then `Accept-Language`,
then the default — with the header's selector as the manual override.

## 3. The documents

### 3.1 Shape

Each module exports a typed structure, not markup:

- the document title;
- the "last updated" date, as data rather than prose, so it can be formatted per
  locale;
- an ordered list of sections, each with a heading and a body of paragraphs and
  lists.

One renderer turns that into `<main><article>`, an `<h1>`, `<h2>` per section,
`<p>` and `<ul>`, with links as real anchors. The renderer is the only place
that knows about markup, so the nine content files stay prose.

### 3.2 What the structure does NOT do

No arbitrary HTML in content, and no rich-text parser. A legal document needs
headings, paragraphs, lists and links, and that is the whole vocabulary. Adding
more would mean the renderer stops being auditable, and these three pages are
exactly the ones where what is displayed must equal what was written.

### 3.3 Translation

The Portuguese is the owner's, corrected only for the product name. English and
Spanish are translations of it, not new drafts: the same sections in the same
order, so the three can be diffed against each other when the policy changes.

## 4. The deletion request

### 4.1 The record

A new table, `data_deletion_requests`, following `contact_requests`'s shape
(0004) rather than inventing one: name, e-mail, telephone, an optional station
name, optional notes, a `status` enum defaulting to new, a hashed IP, and
timestamps. Plus the one column that table has no equivalent of:

**`protocol`, unique, generated by the database.** Eight characters from a
32-symbol alphabet with the ambiguous ones removed — no `0`/`O`, no `1`/`I` —
formatted `PX-XXXX-XXXX`. Generated in a column default so a row cannot exist
without one, with a unique index as the guard; the service retries once on the
astronomically unlikely collision rather than pretending it cannot happen.

Sequential numbering was rejected: it would be easier to read aloud and would
publish how many people have asked to be deleted.

### 4.2 The submission

The path `/contato` already established, reused rather than re-derived: a Server
Action, a zod schema in `src/schemas/`, a service in `src/services/` that
rate-limits on a **hashed** IP (five per hour, the existing ceiling), records the
row, notifies by e-mail through the existing mailer, and redirects back with a
result in the query string.

**The fields are the owner's own list**, from the text they supplied:

| Field | |
|---|---|
| Nome | required |
| Telefone usado no atendimento | required — it is the key an operator searches by |
| E-mail para retorno | required — there is no way to answer otherwise |
| Emissora com a qual interagiu | optional, "se conhecida" |
| Motivo ou observações | optional |
| Confirmação | required checkbox: *"Solicito a exclusão dos meus dados pessoais armazenados pelo PulchatX."* |

The checkbox is not decoration. It is the difference between somebody typing a
telephone number into a form and somebody **stating a request** — and it is what
the screen in §4.3 shows an operator when they act on it.

Two differences from `/contato`. The redirect carries the protocol so the
confirmation screen can show it. And that screen is not a thank-you — it is the
receipt: the protocol, what happens next, and how long it takes.

### 4.3 The screen behind it

A platform-admin screen at `/admin/data-deletion-requests`, modelled on
`/admin/contact-requests`: the list, the detail, and the transitions of the
status enum. It is where an operator records that identity was verified and what
was erased.

**The nav item goes in the Plataforma section**, which Block 20b left last and
admin-only.

## 5. Reachability

`PUBLIC_PATHS` in `src/middleware.ts` is an explicit list, and a path absent from
it sends a signed-out visitor to `/login`. The three addresses are added there.

That list is load-bearing and its own comment says so: this is the same file
whose `matcher` and `next.config.mjs` exclusions have to agree. The e2e proof
for these pages is therefore **a request with no session at all**, not a
signed-in one — a page that works while signed in tells us nothing about the
listener who will actually open it.

---

## 6. What this does not do

- **It does not erase anything.** D3. The screen in §4.3 is where erasure is
  performed, by a person, through the doors that already exist.
- **It does not change `anonymize_member`** or any existing LGPD machinery.
- **It does not add a cookie banner, consent manager or analytics notice.** None
  is described in the owner's text, and inventing one would put a claim on the
  page that the product does not implement.

---

## 7. A limitation the owner should know, and which this block does not fix

This project already records that **an anonymised listener is not recognised
when they come back**: `anonymize_member` (0087) nulls `phone`, and
`phone_normalized` — the column every door matches on — is generated from it. So
the next time that person contacts a Station, no match is found and a fresh
record is created.

That does not contradict the text on these pages: nothing in the owner's policy
promises to refuse a future interaction, and the erasure itself is real. It
matters only if the intention is "this person ceases to exist in the base", which
is not what happens. It is a product decision that predates these pages and is
recorded as still open.

---

## 8. Verification

- **Unit:** the protocol formatter — its alphabet excludes the ambiguous
  characters, and its shape is stable — and the content modules' structural
  integrity: the three locales of one document must carry the **same section
  count in the same order**, which is what makes them diffable and what catches
  a translation that silently dropped a clause.
- **i18n gates:** the existing `catalogue.test.ts` and `usage.test.ts` continue
  to bind the interface labels these pages add. The content modules are outside
  their remit by D1, which is why the structural test above exists instead.
- **pgTAP:** the protocol's uniqueness constraint, the default that fills it, and
  that the table is unreadable to `anon` — a deletion request holds a name, a
  telephone and an e-mail, and is exactly the kind of row a public bucket of
  personal data must never become.
- **e2e:** one journey per page **with no session**, asserting the document
  renders and is reachable; and the deletion journey end to end — submit, land on
  the receipt, see a protocol matching the documented shape, and find the row in
  the database with that protocol.
- The eight gates in the order `portoes-e-banco-local-sujo` records.
